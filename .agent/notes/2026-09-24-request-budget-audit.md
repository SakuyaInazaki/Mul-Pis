# 单次请求预算复核（2026-09-24）

用户指出先前设置的单次输入/输出额度未经真实工作负载校准。确认：上一批只用假 runner 验证文档示例能通过控制路径，没有以真实 H/I 用量证明 20000/2048 合理。

只读检查本地 Pi usage sidecar，按已报告事件统计，不读取提示词正文、任务内容或答案，也不纳入 fake runner 样本：

- 方法研究开发链可核对的真实请求仅 2 次 H、1 次 I。H 的 provider 输入（含缓存读写）为 475、623 tokens，输出为 161、289；I 输入为 1330，输出为 478。相应请求曾声明 H 输出上限 2048、I 输出上限 4096。这些小样本均未碰到输出上限，但不能据此校准复杂多案例或多步研究。
- 另一个真实主 Pi 工作流的 sidecar 中，去重后有 729 条已报告 provider 事件，另有 9 条非 reported 事件未用于分位数。输入中位数约 50532、P90 约 105609、最大 150388；输出中位数 511、P90 5954、最大 24724。若错误地对主 Pi 使用 H 示例的 20000 输入/2048 输出限制，其中 623/729 条输入及 168/729 条输出会超过该数值。主 Pi 当前并不受方法研究的 perPrompt 限制；这些统计也不能用于直接校准 H/I。
- sidecar 是 SDK 可见 usage，不是完整账单；样本集中于本地开发与一个工作流，不构成跨任务统计保证。输入 cap 在代码中以 UTF-8 字节加封套余量做保守 token 预留，与 provider 实测 token 不可直接相比。

因此仅在公开文档将示例数值明确标为未校准示意，不把它称为合理默认值，也不自动扩大或撤销调用方资源授权。真实 H/I 上限应由固定任务族的试跑分布、模型上下文能力、组装 payload 预检与调用方成本/时间预算共同确定。未运行新模型调用。
