# Repair-loop liveness and private continuation

Source review found that a read-only objective assessor and M04 judgment could
receive unchanged host validation feedback repeatedly without changing their
repair strategy. The host now compares stable validation class, frozen plan
identity, and actual returned-read coverage. An unchanged ineffective repair
switches to a fresh independent read-only judgment over the same frozen
materials; the new session must return every required range again. Genuine new
read or validation progress can support further work. Repeated structurally
invalid M04 drafts with identical content do not create duplicate proposal
submissions. Unknown proposal or merge effects keep their existing
reconciliation path.

If distinct safe repair strategies cannot make progress, the host records a
typed workflow-repair-needed action while the original mission remains
incomplete. The action is never a scientific verdict or a request for human
permission. A current host-reviewed repair plan must bind the authenticated
terminal carry, action, and tested replacement source before any new control
request is prepared. The public request descriptor remains fixed.

The private repair-state.json receipt contains control-only fingerprints and
strategy state. It is included in encrypted result and authenticated carry, but
is not accepted as evidence-read credit, selected scientific output, or
authority to repeat a past operation. The host retains request accounting
across fresh local sessions. No fixed turn, call, time, cost, or output budget
was added.

This is a source-proven liveness repair for later executions. A running
workflow using an earlier source is unchanged, and its current behavior cannot
be inferred from this source audit. Focused synthetic tests exercise unchanged
repair feedback, genuine new progress, complete rereading, safe pending
actions, proposal deduplication, private receipt transport, and no replay.
