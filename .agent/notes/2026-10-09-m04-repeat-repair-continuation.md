# Continue M04 judgment after repeated unchanged repair evidence

The M04 repair loop treated a repeated normalized read or validation failure as an exhausted fresh-context strategy. After same-session feedback and one fresh-context failure, it emitted `workflow-repair-needed` solely because the same failure recurred. An offline production `runM04` regression reproduced this terminal before a scripted later valid judgment could be reached.

M04 now continues with a genuinely new read-only research context when identical repair facts recur. The existing handoff checks still require an empty independent session, frozen model and tool grant, current snapshot-bound knowledge, and fresh full returns for every required M07 file. An unresolved proposal or merge intent still blocks a context reset. A repeated rejected draft reuses its exact receipt; no draft or merge is replayed. Actual provider aborts, invalid read tool returns, changed evidence, unsafe context boundaries, and unresolved effects retain their existing failure paths. No count, elapsed-time, or monetary limit is used to declare judgment or scientific success. Model calls themselves provide a natural wait between attempts, so no separate retry delay was added.

Follow-up audit found that the normal fresh M04 path cached its message before the first replacement context. This skipped the knowledge snapshot check on every replacement, and the M01-continuation path skipped it after its first replacement. A synthetic concurrent writer advancing the store's current snapshot after either of two invalid replies reproduced stale judgment admission. Every fresh handoff now checks that the current knowledge snapshot still equals the original before opening a replacement context, including when its message was cached. A changed snapshot yields typed `m04.knowledge` repair without another model request or M04 store effect.

Offline checks: `node --test --test-concurrency=1 test/m04-required-m07-reads.test.ts` passed 46 tests, including recovery after four identical malformed replies, repeated invalid drafts without duplicate submission, repeated missing reads with proof from the final session, prompt abort propagation, and changed-snapshot rejection before first and later replacements. `node node_modules/typescript/bin/tsc --noEmit -p tsconfig.json` passed. The production regression failed on the original code at the repeated-state `WorkflowRepairNeededError` branch before the change. The stale-snapshot cases failed on the first repair commit before the follow-up fix. An earlier `npm run typecheck` invocation was rejected by automatic review because npm could contact the registry; direct installed TypeScript completed without npm. No real provider, network service, private mission, GitHub push, or CI run was used.
