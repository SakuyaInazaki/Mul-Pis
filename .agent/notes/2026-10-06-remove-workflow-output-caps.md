# Remove workflow-set output limits

The user directed removal of every workflow-imposed model output limit. This supersedes the earlier adaptive-output reservation policy recorded in `2026-10-06-adaptive-provider-reservation.md`; that earlier note remains historical evidence, not the current request policy.

For the metered DeepSeek Flash campaign, a fresh read-only `/models` response must identify the exact `deepseek-flash` model and its service-side `max_output_tokens` and `context_window`. The host uses that reported provider maximum for the SDK model and outgoing Chat Completions `max_tokens`, and reserves the full provider maximum under the unchanged single 30 CNY ceiling. It neither shortens output to fit the remaining budget nor mistakes an omitted `max_tokens` for unlimited generation. Missing or contradictory model metadata stops before a provider request. Current [DeepSeek model metadata documentation](https://api-docs.deepseek.com/api/list-models/) gives `max_output_tokens` as the maximum accepted request value, and [Chat Completions documentation](https://api-docs.deepseek.com/api/create-chat-completion/) states that omission has a smaller default and that input and output share the context window. The documented current example is 393216, but code does not freeze that number as an artificial maximum: a different valid live server maximum is reserved exactly.

The global money limit, historical billing commitments and unknown holds, peak native-CNY price basis, conservative input-bytes estimate, output-accounting margin, and fail-before-transport admission remain. A known priced `length` response is settled and marked incomplete with an `output-limit` stop reason; it is never success. The rejected-request diagnostic may describe a smaller affordable allowance for explanation only; it cannot set the outgoing output parameter. A live provider-output profile is now required even under legacy price estimates; retired caller output-cap fields are discarded rather than applied. No paid request or public release was made in this change batch.

The user's later instruction also removes workflow time and count quotas while retaining file/data-size limits. Total and per-prompt provider-call cap fields are ignored in every new DeepSeek campaign, including legacy-priced campaigns; request counts remain as audit facts and every request still needs its own full-bound reservation under the global money ceiling. Pi's strict runner never imposes a call-count stop. Disabled hidden SDK retries preserve per-transport accounting rather than limiting a research objective. Old call-cap values remain readable in historical records, but they do not govern any new transport. Read-only probe timeouts and the SDK HTTP fault timeout remain communication-failure safeguards, not campaign lifetime limits.

Factory-attested confined file reads now record only the relative path, returned UTF-8 byte count and an explicit nontruncation flag. Read failures carry a bounded redacted error class/code/message; arbitrary custom tools cannot claim full-read evidence. Tool logs omit raw read results and write/edit content or command arguments. These telemetry changes do not relax existing file-size or tool-authority boundaries.

Encrypted carry validation no longer imposes a 1000-request, 1000-rejection, or 2000-ancestor record count. GitHub workflow-history verification no longer stops after twenty pages; it still requires complete ordered pages through the signed anchor and enforces GitHub's requested 100-items-per-page response shape. The existing bounded carry and private input bytes, exact schema, and uniqueness checks remain. Confined write grants still require explicit unique relative file names, but have no sixteen-file count ceiling.
