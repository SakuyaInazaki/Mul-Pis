# M09 交付必须对照轨迹内历史最优候选

## 为什么

- RB-A8-01（P0，多篇消融 + 理论证明）：最终交付必须是历史最优候选，不是最后一轮产物。可检查形式是「候选池有显式 best 指针、终局取 best」；违反的表现是「最终产物比中途某一版慢」。理论支撑是 POLCA Thm 2（从历史最优出发把期望步数从指数降到线性）。
- RB-A8-06（P0，多篇测量）：任何加速数字都要能回答「分母是谁、聚合怎么算、是 kernel 级还是端到端」，缺一项即不可引用。
- RB-A8-04（P0）：交付前要能说明认证范围，不能把迭代期间的几个用例当认证。
- RB-A8-05 / RB-A13-02（P0）：接受权归确定性引擎。

改动前，交付链是「M08 选材料 → M04 判定可交付路径 → M09 复制 included」，三步都由主 Agent 和模型判断驱动，**没有任何一步读过候选归档**。全仓 `globalCandidateBest()` 的调用者只有 M07 内部与控制台，交付侧一次也没有。于是交付一个比中途某一版更差的候选不会被任何机制发现。

## 改了哪里

- 新增 `src/stages/delivery-evidence.ts`：
  - `collectDeliveryEvidence(ws, deliveryRoot)` 遍历工作区里每个可读的 M07 目标，用既有的 `candidateSearchSnapshot()` 取可读归档与同口径最佳，按 **sha256 字节身份**判断交付副本里出现了哪些归档候选（文件改名不影响判定），并汇总测量口径披露：口径清单、有/无同口径参考测量的指标数、终态与未终态外部评测数、逐例通过/失败/未知。
  - `assertDeliversHistoricalBest(evidence)` fail-closed：交付里出现了某对象的归档候选，而同口径历史最佳是另一个未被交付的候选时，抛 `m09.superseded-delivery` 并写明最佳候选与它的口径。
  - 没有归档候选的交付（例如纯文档交付）得到空对照，行为与改动前一致。
- `src/stages/m09.ts`：复制交付副本之后、建立说明会话之前做对照，结果写 `delivery-evidence.json`，作为 data 进入 P09 说明会话（并明确要求没有参考测量的指标不得写成相对基线的收益），并保存在收口回执的新字段 `deliveryEvidence` 里。
- 新增共享测试辅助 `test/helpers/candidate-goal.ts`：写出一个带冻结候选归档的 M07 目标。
- 新增 `test/delivery-evidence.test.ts`（4 项）与 `test/m09.test.ts` 的一项集成用例：交付非最佳 → 拒绝并指名最佳；交付最佳 → 通过且回执里记录对照与口径；无参考测量 → 显式标注没有分母。
- 文档：`docs/implementation/design.md` 的 M09 段落。

## 验证

- `test/delivery-evidence.test.ts` 4/4、`test/m09.test.ts` 4/4。
- 全量测试结果见本批次最后一个提交对应的 note。

## 破坏性

收口回执 `closure.json` 增加必填字段 `deliveryEvidence`；历史回执没有这个字段。按本轮规范，重构允许破坏历史工作区格式：旧回执仍可读，但新代码生成的回执与旧回执字段不同。

## 边界

对照只建立「交付字节 ↔ 冻结候选字节」的身份关系与「已记录测量口径」的披露。它不做端到端性能门（需要测量层，属 A4），不做隐藏配置重验（需要评测层，属 A3），也不聚合加速比——三个聚合数需要先有 harness 自己的参考基线。
