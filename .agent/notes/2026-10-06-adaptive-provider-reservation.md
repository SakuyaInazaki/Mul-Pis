# Adaptive provider reservation for a single campaign ceiling

The DeepSeek campaign host now computes the largest output-token cap that fits the remaining global CNY ceiling for each serialized provider payload. It returns that cap in the actual SDK `onPayload` request and reserves the exact outgoing payload bytes plus that output cap and the existing accounting margin, using the higher of configured conservative rates and SDK rate estimates. The configured output-token cap remains an upper bound. A request with no affordable output token still fails before transport; a provider length stop remains incomplete.

Each new host request audit row retains the effective output cap. The encrypted carry validator accepts the new field while still reading earlier rows that lack it. A locally refused subrequest after one or more fully settled subrequests can produce a host-certified `partial-settled` error with the settled request count and stop reason, without treating the whole M07 operation as never issued or erasing settled spend. A separately certified terminal length response records that a response arrived and its provider requests settled, while the task remains incomplete. These dispositions require an exact active no-tools set or the host-attested confined file-tool factory; other tool scopes cannot derive settled whole-operation state from provider usage alone. Ambiguous transport and response failures remain unknown.

Synthetic, no-network runner tests cover reduced outgoing caps through the pinned SDK's actual HTTP-body construction, exact reservation, a settled first tool-loop response followed by a local pre-transport denial, and a settled but truncated length response. This does not establish scientific task completion or actual provider billing.
