# M07 reviewer snapshot file-count limit removal

The M07 repair loop used to refuse a reviewer snapshot after 1,000 copied work files, even when total bytes stayed within the retained 64 MB capacity. The task asked to retain file-size limits while removing workflow-imposed file-count stops. `snapshotRoundForReviewer` now checks cumulative file bytes, symlinks, and special files without a file-count cap. A synthetic offline regression creates 1,001 tiny files, verifies the independent reviewer can read the copied last file, and expects a ready task. The analogous branch-fork evidence copy also had a 1,000-file stop. This was removed as well; its 64 MB file-byte limit, per-file safety checks, symlink/special-file exclusion, forbidden-auth material checks, provenance manifest, and copy-byte verification remain. The many-file regression also requires the branch checkpoint to be available. No scientific adapter, private case, real model, paid run, commit, or push was involved.

The same loop had a separate indirect builder-output stop: it placed the full persisted builder report into the fresh reviewer prompt, then rejected the prompt at the frozen policy's handoff-character limit. Short reports remain inline. When the complete prompt would exceed that limit, the controller freezes the complete report as exact ordered, 8,000-byte-or-smaller UTF-8 segments inside the independent reviewer's read-only snapshot (the verbatim original remains persisted at the builder report path), instructing range reads and a blocked verdict if the evidence cannot be read. The combined snapshot still observes 64 MB, and an oversized reviewer reply still observes its existing 512,000-byte file limit. A second synthetic offline regression uses a 190,000-character single-line builder report and checks that the reviewer can reconstruct every byte without an inline prompt overflow or duplicate storage against the snapshot byte limit.
