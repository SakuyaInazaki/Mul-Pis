# True Pi session fork, 2026-10-05

Implemented a controller-gated checkpoint and fork contract in the session runner. A checkpoint requires an idle, successfully completed prompt and a settled external-operation assertion. It copies the persisted Pi JSONL, parent grant spec and input manifest to runner-owned checkpoint files. Fork verifies those byte copies against the current source, opens the snapshot with a separate Pi `SessionManager`, creates a new session from the frozen leaf, gives it a fresh scratch directory and explicit child tool grant, and commits a lineage receipt before the child handle is returned. The original parent remains appendable. A branched session cannot resume without its committed lineage receipt; a resumed parent needs a completed usage ledger before it may become a fork source. Evidence bindings must name frozen copies; old paths in historical tool results are retained and are not silently rebased. A conservative equal-or-narrower grant rule currently prevents branch history from raising tool authority. A future independently authorized transition to bounded frozen read-only access would need a separate verified grant contract; it is not an intrinsic limitation of the context modes. The fake runner mirrors checkpoint and fork semantics for controller tests.

Writable forks now require a typed workspace binding in the checkpoint's frozen controller manifest. The runner checks the parent and child roots, an authorized task-container base and work-leaf layout, a child ownership marker, disjoint roots, and byte-equal frozen-to-child file mappings. Audited campaign custom tools also persist a factory-derived root and relative write allowlist in the frozen parent and child specs; names alone do not authorize a custom-tool fork. The live Pi runner can attest that custom grant only for its own active handle using the factory's private tool identity; the boundary dispatcher verifies and records the effective root/allowlist when a controlled wrapper narrows requested execution to audited custom file tools. A read-directory-to-read-directory fork is currently unsupported until a frozen read-root authority schema exists. Branch lineage explicitly says `branch-exploration`; role changes do not imply independent review.

Offline SDK integration tests cover two sibling branches, a later parent turn excluded from each child, original tool-result payload retained in JSONL, independent session IDs/files/scratch, compaction history, immutable manifest validation, authority non-elevation, audited custom-tool root separation, and no ancestor usage recounting. No real model or network calls were made. This is context and runner isolation, not an OS sandbox or a claim that a model read the frozen evidence. Native bash still has the host user's file and network permissions. No publication or repository push was performed.

The shared campaign budget now records the factory-derived custom file authority in the persisted spec. A complete length response is conservatively charged and synchronously stops the campaign before a further tool-loop request; an error response stops and retains the unknown worst reserve before it is forwarded to Pi. Offline stream regressions attempt a later request and verify denial. An earlier integrated working snapshot passed the complete offline suite at 432/432 with TypeScript typecheck passing; final publication requires the parent’s exact-tree rerun after subsequent integration changes. No paid model request was made for this verification.
