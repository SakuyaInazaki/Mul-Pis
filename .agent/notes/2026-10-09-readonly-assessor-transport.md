# Read-only assessor provider transport continuation

This change is a synthetic, offline engineering regression. It is not a real DeepSeek run or scientific validation.

The default `mission.run` previously converted every assessor prompt exception into `assessment-failed` and stopped the loop. A test reproduced this with a host-classified HTTP 503 provider-stream error from a read-only assessor: the scripted next valid proposal, bounded M07 report and M04 review were never reached.

The assessor now retries only a host-classified transient transport failure in a genuinely fresh read-only session. It saves a redacted transport observation and control-only repair receipt before another prompt, checks the frozen evidence, and uses abort-aware exponential backoff. No fixed number of retries, elapsed-time limit, fee limit, or scientific stop is introduced. A cancelled prompt stays cancelled. Auth failures, static request rejections, context overflow, and unclassified exceptions hold incomplete with separate control outcomes; none authorizes M07 dispatch or scientific closure.

The default-run regression verifies one 503 followed by a valid task and exactly one M07/M04 pair. Unit regressions exercise four consecutive 503s before a valid proposal, typed nonretryable outcomes, and cancellation during the retry wait. The fake runner supplies a synthetic redacted diagnostic through the same SessionHandle method used by the real Pi runner; it makes no provider or network call.

A later offline regression changed one frozen evidence file during the transport backoff. Before correction, the host opened a second assessor on altered bytes. The host now rehashes every frozen file after the wait and admission check, before opening a fresh assessor; changed evidence suspends assessment without another provider prompt.

The first retry test injected a diagnostic into FakeSessionRunner. A separate real-path audit found ordinary Pi sessions did not create TransportProbe unless campaignBudget was present. Default mission Pi sessions have no campaign budget, so that synthetic result did not establish live classifier input. Pi now observes redacted fetch status, body-read faults, and allowlisted error codes for ordinary sessions without adding campaign caps or request reservation. It discards each probe after its prompt. An offline default `mission.run` fixture uses a genuine PiSessionRunner for the failed HTTP 503 assessor, then a fresh scripted assessor for the valid proposal; the task executes and M04 reviews once, and the original objective stays open. No provider or network call occurs.

For HTTP 200 or unknown status, the assessor retries only when the host observed a fetch/body-read interruption or an allowlisted network code. A local `runner.model` exception after a successful 200 remains unclassified, including after an SDK internal retry from a previous network failure. The probe resets per-request facts at each physical fetch to prevent an earlier failed attempt from tainting a later response. The offline Pi fixture also checks a 200 response-body interruption. These tests are engineering controls, not a real DeepSeek long run or scientific validation.

A separate offline test uses Pi's actual AgentSession, ModelRuntime, and OpenAI SDK with a stubbed fetch returning HTTP 503. It verifies the ordinary, no-campaign assessor receives one redacted diagnostic and keeps failed usage UNKNOWN. Pi's agent retry settings initially sent four physical requests before the host could persist one failure. Original-objective read-only assessors now disable SDK-level repeats so the host can persist each failure, recheck evidence, then retry in a fresh session. The no-campaign probe and fetch wrapper are scoped to those assessors; mutation-capable sessions retain their existing transport and retry settings. A simulated SDK-owned signal abort on a 200 body read records its abort source and stays cancelled.

An SDK-owned abort before any fetch has no transport diagnostic because no request was observed. The live SDK signal still produces a typed aborted control result and an aborted usage outcome. A default mission fixture identifies the first persisted MISSION attempt by its start sequence; run IDs and filenames are not chronological.
