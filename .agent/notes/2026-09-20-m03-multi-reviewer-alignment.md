# M03 多成员质询对齐

用户澄清原流程首轮由三个不同 AI 质询；当前决定先用三个独立 DeepSeek 会话模拟这一步，并授权将 M03 扩展为工作区可选的显式成员列表。

- 每个成员项直接写完整 `provider/model[:thinking]` 模型引用，允许多个成员暂时使用相同模型；只有缺省成员列表时才回退旧 `roles.reviewer`/`roles.default` 单 reviewer 配置。三个 DeepSeek 会话只构成同模型多会话实验，不称为三种模型验证，也不规定所有工作区必须配置三家或三个成员。
- 三个成员读取同一冻结的原问题与 M01/M02 完整产出，各自在全新隔离会话出题，互不读取其他成员的题目、回答或评价。
- 所有题目先收齐，再由同一个 M01 原会话按成员顺序逐组三次作答；M02 完整产出只在第一组显式附带，后续组沿用会话中已经存在的材料。
- 每组完整回答只返回原出题成员的原会话，由该成员评价自己的题目。全部评价齐备后才形成一个批次进入 M04，由研究会话统一作科学判断，不以多数票或一致性裁决。
- 任一成员失败都必须显式保留并阻止整批被写成完整完成，不能静默跳过。
- 未配置成员列表时保留旧单 reviewer 兼容路径；本轮不修改 `workflow/v1.0/` 原文，不调用真实模型，不重写既有 M03 run。

实现已完成并通过离线验证：`npm test` 为 121/121 pass，bundled TypeScript `tsc --noEmit` 与 `git diff --check` 均通过；独立审查没有 blocking 发现，相关 fake 测试为 27/27 pass。成员失败路径已覆盖：manifest 会记录该成员 `failed` 与失败原因，整个 M03 run 结束为 `failed`，不生成可冒充完整批次的“逐题评价”聚合，因此不能作为 completed M04 输入。

有限重试指纹使用实际解析后的成员模型多重集合，并包含解析后的上游 run，避免仅改成员标签或输入顺序绕过同一受控义务，也避免不同真实模型组合被误判为同一义务。`latestCompletedRun` 的排序已保留毫秒时间精度，修正同一秒内多个 run 可能选错上游的问题。
