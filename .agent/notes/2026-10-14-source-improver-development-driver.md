# Source-backed improver development driver

This batch adds an executable I program entry and a fixed development search host. A prepared read-only source snapshot starts a separate child process for the selected I program. The child verifies its loaded source and fixed module/export, then returns one action at a time. The host owns the registered development evidence, configured improver model calls, source proposal callback, development evaluation callback, usage ledger, candidate registration, and frozen selection record. The action state contains development observations; protected confirmation outcomes are outside this driver.

The human seed I reads the available development evidence, asks the configured model for a falsifiable JSON analysis, proposes one source candidate, requests one development comparison, then selects or reports no winner. An edited I module can choose different evidence, action order, proposal brief, model prompt, candidate comparison, or terminal decision. The host validates each action and requires a selected candidate to have been generated and development-evaluated in the same search. A ready source candidate must have a committed, engineering-passed receipt and prepared source binding. The host does not perform admission or activate source.

The source bridge receives only a narrow environment and no host tool grant. This is process and context separation, not an operating-system filesystem or network sandbox; source programs are still JavaScript. The parent retains its own source and usage checks. Model JSON parse failures enter development state for I to repair; provider failures and unsettled usage make the search incomplete. The driver has no implicit token, character, candidate count, or elapsed-time stop. A trusted caller can cancel it explicitly.

A later receipt audit closed a cost-completeness gap: even if reported token usage is complete and has zero unknown events, an unpriced provider cost cannot produce `selected` or `no-winner`. The search instead records `incomplete`, preserves the observed session/usage and a cost-specific reason, and writes no immutable selection. An offline fake-provider regression covers this state.

Offline tests load two different I source commits in real child processes and observe different decision order. They also cover invalid candidate selection, incomplete usage, JSON repair, provider failure, and the existing source candidate path. These are engineering checks, not evidence of real-model H or I research gain.

## Cancellation, partial costs, and selection freeze repair

The I action contract can cite registered prior model observation IDs. The trusted host passes those exact observations, including raw failed JSON text, to the next model request. The seed uses this on a parse error. The source child is forcibly terminated on explicit cancellation or close; fatal startup reports an error and exits. The candidate builder now aborts its active model session on the caller signal, and controller engineering checks run in cancellable child processes. Candidate rejection retains its session, usage, changed-file list, and available patch.

Trusted proposal and development-evaluation callbacks can report each settled usage summary before returning or failing. The host retains reported partial usage on failure and marks the search incomplete. A complete immutable selection receipt now includes the caller-supplied baseline bundle and executor-source identity, development-set ID, all action and model-session records, all registered candidates and evaluations, and observed token/cost totals. The receipt remains a development selection, not admission. The host has no implicit count or time limit; callers must supply and use an explicit cancellation signal for unattended searches. This repair was checked with typecheck and fifteen offline tests, including actual loaded I process cancellation, fatal startup, builder prompt cancellation, and hanging engineering-check cancellation.
