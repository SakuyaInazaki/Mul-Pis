# Local mission evaluators

A local mission may name a trusted host evaluator in `research.config.json`:

```json
{
  "roles": { "research": "provider/model", "execution": "provider/model" },
  "localMission": { "evaluatorId": "host:file-sha256" },
  "concurrency": 1,
  "tools": {}
}
```

The evaluator ID resolves only through `registerTrustedLocalMissionEvaluator` in host code. Objective JSON cannot load a module path. The default CLI and Pi local mission entry points use this same registry. An absent, unsupported or preflight-declined evaluator produces a host-observed `supply-capability` pending action before either finite or open-ended missions call the assessor. This is a recoverable host capability gap; the host does not infer that only a person can repair it. Capability observations have content-bound filenames, so installing the evaluator can resume the same mission without replacing the earlier observation.

For a private lab evaluator, install reviewed host code in the same Node process before the CLI entry point (for example, an operator-controlled `node --import /private/trusted-evaluator.mjs src/cli.ts mission run ...` launcher). The bootstrap registers a stable ID and version with `registerTrustedLocalMissionEvaluator`; workspace `research.config.json` selects that ID, and the original-objective request uses an obligation type supported by the registered evaluator. Each new `mission run` or `mission resume` process must load the same trusted bootstrap. Neither model output nor the mission request names a module. The evaluator's `preflight` receives host-frozen original input identities (including material-bundle item identities when present) and observed host capability facts; it can decline missing experimental capability without rewriting the user's obligations. No private lab algorithm is bundled here.

`host:file-sha256` is a narrow production example. It supports obligations with `type: "file-sha256"` and a lowercase `expectedSha256` digest in the authored original-objective request. It compares candidate file bytes to that digest. It does not assess scientific meaning, performance, completeness, or open-ended closure. Other obligation types require separately reviewed host registrations.

The host copies bounded candidate bytes before evaluation and gives the evaluator a new private `host-evaluator-output` directory under the M07 task root. The evaluator may write UTF-8 text logs (`kind: "text"`) or structured JSON results (`kind: "json"`) with `observation-` filenames, then declare every member. The host rejects missing, extra, nonprivate, nonregular, escaping or changed members; it freezes exact bytes under a separate `host-evaluator-snapshot` directory. Each observation receipt records its name, kind, source and snapshot paths, size, digest, evaluator ID/version, mission/run/task identity and candidate names/digests. Candidate, observation and original input evidence remain distinct. These are physical file bounds, not an experiment-count or cost quota. Binary observations need an explicitly reviewed text projection before this evaluator interface can admit them to M04 full-text review.

The host saves `passed`, `failed`, `not_run`, or `unknown` checks with genuine observation evidence and limitations. A failed addressed task is rejected. Checks outside the bounded task can remain failed or unknown while an accepted task supplies a locally reviewed incumbent. The selection receipt maps every original obligation to `passed`, `failed` or `unknown`; selection never changes the user-authored obligations or claims open-ended closure. M07 `review` and `finish` persist accepted checks only when its own controls pass. A fresh M04 session must return the complete required text from the exact M07 checkpoint, including all admitted observations. The host checks the M04 source, read coverage, completed transaction, mission/task/evaluator identities, observation members, and candidate bytes before recording selection. It also checks the exact checkpoint candidate and observation copies against evaluator hashes. A later process rechecks these bindings and makes selected files and M04 evidence available to the assessor under run/task-specific evidence names. A completed mission retains its historical checkpoint, but `status`, `step` and `run` refuse to report it as currently valid if selected evidence has changed or vanished. An evaluator pass alone does not select a candidate or fulfill the original objective. Open-ended missions remain incomplete under the current closure policy, even after local selection.

The default evaluator only handles files within the M07 task's bounded output/review area. It does not convert binary data for M04 scientific inspection; an evaluator that needs visual or non-textual evidence must provide a reviewed conversion and explicit limits. No task-specific benchmark or acceptance threshold is embedded in the generic host. This is a trusted same-UID local workflow, not an OS sandbox or cryptographic attestation against a process with the same filesystem privileges. A trusted evaluator receipt is not re-executed on restart; the host verifies its persisted bindings and bytes. The included `host:file-sha256` check and the offline CLI test's synthetic byte-count measurement establish no scientific correctness.

Selection receipts created by the earlier unqualified-name prototype cannot be silently rewritten into the new run/task-specific evidence namespace. Reopening such an existing checkpoint requires an explicit, separately reviewed migration. This source branch has no migration command and does not claim old checkpoint compatibility.
