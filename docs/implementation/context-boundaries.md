# Context boundaries and session lineage

Mul-Pis keeps the M01–M09 workflow and the C/K/E/J/Q/D/X knowledge store. A model's **role** answers what job it performs and which configured model serves it. Its **context boundary** answers what prior conversation it inherits. The two are deliberately separate.

The controller selects one of three explicit boundaries through `src/context/boundary.ts`:

| Intent | Boundary | Meaning |
| --- | --- | --- |
| New bounded work | fresh | New session; receives only declared task materials and capabilities. |
| Independent judgment | fresh | No actor or other reviewer conversation is inherited, even if the same model is used. |
| Causal continuation | continue | Reopen the exact persisted session for the same actor's next turn; the persisted role, model and tool grant are verified. |
| Competing exploration | fork | From a completed, frozen Pi leaf, make an independent new session carrying that root-to-leaf history. It has its own workspace and frozen original-evidence bindings. |

These are decisions based on the work's causal relationship and required independence, not rules such as “reviewer always fresh.” In M03, a reviewer starts fresh to write questions and continues that same reviewer session to evaluate its own answer; M01 continues to answer the questions. M02 independently evaluates M01's visible output without inheriting its private dialogue. M06 checking and applicability, M08 external review, and M09 delivery checking remain fresh. M07 builder repairs continue the same actor; every independent review is fresh. M07-to-M04 feedback is judged in a fresh research session. First M04 may continue M01 when the original history and original permission suffice; later M04 starts from explicit feedback and current selected knowledge.

Every stage-opened session writes a boundary receipt into its run record: intent, mode, reason, declared evidence references and their status, actor role, model, capability summary and any parent identity. `linked` paths and `index` entries are pointers only; they are not proof that the model read the underlying content. Existing runs lacking a receipt remain readable but must not be interpreted as having a true fork.

The dispatcher waits for the run receipt to be persisted before returning a handle that a stage can prompt. It checks the **effective persisted** runner spec, not just the requested one. When a private campaign adapter replaces native execution tools with confined custom tools, the runner must additionally attest those tools from its live factory identity; the exact task root and bounded write allowlist are then recorded with the actual grant. A wrapper's matching tool names or forged spec metadata alone cannot claim an audited narrowing. A continuation must return the same session ID and files as the parent. A fork must return a different session plus a committed lineage sidecar bound to the exact checkpoint, leaf, child and evidence; a fresh session with a branch-sounding label fails this check.

For a true fork, the runner checkpoints an idle, normally completed parent and freezes the exact Pi JSONL leaf, parent spec and input manifest. It uses a **separate** `SessionManager` to create a child file from root to that leaf; it never switches the live parent manager onto the child. A child gets a different session ID and scratch directory. The copied message history does not copy external files or undo previous tools: the controller separately binds immutable original evidence, maps previous paths to the child-visible copies, and gives the child its own writable task directory. A copied tool result's old path remains historical data, not authority to write there. A frozen workspace binding authorizes the child root and enumerates source-to-child file copies; the runner checks this separately from conversation history and tool kind, so an unrelated read or write directory is not accepted merely because it uses the same grant name. Fork history does not itself confer tool or knowledge-store authority. This implementation conservatively rejects child tool grants broader than the parent grant; a future controller-authorized transition to bounded read-only frozen feedback would require a separately recorded capability decision and tests. A fork cannot automatically write an adopted record. Cross-model forks are rejected until history compatibility is demonstrated. A summary or branch-summary may guide navigation but cannot replace source bytes or actual reading.

Competing M07 candidate branches retain the same frozen task obligations, checks and baseline. Resource-sensitive measurements must be serialized so parallel branches do not contend and invalidate comparisons. Reviewer `ready`, a report, a saved path and an execution exit code remain insufficient for acceptance. The M07 controller checks the frozen artifacts and actual verification; M04 alone judges whether a candidate lesson becomes an applicable adopted experience in the knowledge store. A later run must explicitly select pinned experience refs and recheck current limits. Selected, loaded, followed and beneficial are separate observations.

A host-measured task can opt into `runMeasuredEvidenceHandoff` before the normal independent review. The same actor first produces its implementation; the host verifies the source; that actor then reads the newly generated evidence and finalizes its report and pending lesson. The helper compares source and evidence bytes before returning, requires a successful post-measurement evidence read, and combines usage from both prompts. It does not remeasure after finalization, silently repair claims, or adopt knowledge. This addresses the causal mismatch in which an actor cites an older timing run while the reviewer sees a newly overwritten verification file. The private campaign uses this reusable helper; other adapters must explicitly supply their host verifier and full-file evidence-read contract. Byte checks are integrity checks at the handoff, not an OS sandbox or proof of faithful reasoning.

M04 callers may require specific frozen M07 evidence files through `requiredM07ReadPaths`. These safe relative paths enter the actual research prompt. The controller verifies the returned text ranges before any proposal submission or merge; mentioning a file or choosing no proposal does not satisfy a declared full-read obligation. The private end-to-end campaign requires the selected candidate, verification and lesson candidate. A genuine no-proposal judgment remains valid after those reads.

The private M07 archive retains each round's complete explicit reviewer feedback and visible reviewer report as bounded private files, plus the controller's explicit review decision. Its JSON is an index. An earlier short inline limit of 2,000 characters/eight lines could silently exclude genuine rationale; the current archive writes the complete text, redacts credential values, validates the files on load and fails visibly when a hard storage bound is exceeded. It never captures hidden model thinking or treats a path to a deleted temporary file as preserved evidence.

The implementation uses the [pinned earendil-works/pi 0.85.1 `SessionManager.createBranchedSession(leafId)`](https://github.com/earendil-works/pi/blob/e4c75a73222ae2c72abb5f5314fa35ee8effc508/packages/coding-agent/docs/session-format.md) as the history transport. It does not treat the Pi API as a file sandbox, replay engine, scientific evaluator, or context-completeness guarantee: compaction may remove older messages from what the model actually sees even though the original JSONL remains retained. The code is inspired by [Humanize RLAR's continuing actor/fresh reviewer](https://github.com/humanfia/humanize/blob/caac620fe5c39ab6d7ae0ab6675ad23a1300a3e0/src/hmz/flows/builtin/rlar/__init__.py), [KDA's task contract and promotion evidence](https://github.com/NVlabs/kda/blob/ef6ce617693ef0782b3ecb9f37e39bbf10226a90/docs/agent-flow.md), and [Compound Engineering's documented reusable lessons](https://github.com/EveryInc/compound-engineering-plugin/blob/9af474a70e7f2a844338519ad9e92aafbd92d4fb/skills/ce-compound/SKILL.md). These are mechanism precedents, not imported code or claims that those projects implement Mul-Pis knowledge adoption.

## Original objective versus bounded execution

A finite M07 child can pass its own checks without satisfying the user's broader objective. The reusable `objective-progress` layer keeps an original contract and source inputs separate from adapter-scoped task checks. It records model-authored unresolved issues and a proposed next task, and never closes an open-ended strongest-attainable objective from candidate acceptance or a model's unsupported completion claim.

The objective assessor is a fresh, read-only workflow session. It receives frozen copies of the contract, all declared original inputs, selected source and measurements, and current attempt/knowledge evidence. Required returned text ranges are verified before its proposal can dispatch. The host validates scope and authority rather than choosing the scientific strategy; a proposal outside the adapter's capability is retained unchanged with an explicit boundary.

`runOriginalObjectiveLoop` is the same loop used by the private driver and offline fake-runner tests. After each admitted child, the driver preserves its evidence, processes an accepted child's evidence through M04, updates the selected-candidate and knowledge provenance, and reassesses the original goal. No-advance results stop immediately. Actual budget, time, capability, model-reported block, unsupported closure and execution failures remain distinguishable; none is an objective-success substitute. Each iteration and assessment has a private retained record.

The final status separates `boundedRunOutcome` from the original `objectiveOutcome`. An incomplete objective returns nonzero with its typed reason and continuation checkpoint even if the bounded workflow was healthy. The checkpoint describes a new admitted run, not transparent replay of a terminated process. Historical successful runs retain their original evidence and prove only their recorded bounded scope.

## Cumulative fee observations and authenticated continuation

New runs do not use a CNY total to admit or stop requests. The original signed seed and authenticated carried ledger still establish prior-attempt commitments before model calls; a missing, stale or unverifiable carry cannot silently restart accounting at zero. New accounting-only continuation retains the verified historical aggregate and uncertain holds as historical facts, then records post-transition settled estimates, uncertain amounts and unpriced requests separately. None is a provider invoice. Missing or expired currency pricing makes the CNY observation unknown rather than a zero charge or an automatic stop. Provider output limits, model/endpoint identity, input confinement, unresolved external operations and research evidence checks remain independent controls.

If a branch fails while an execution operation remains unknown, the driver does not select it or declare the goal complete. It retains accepted and failed artifacts, updates the objective checkpoint from later attempts, and explicitly records the reconciliation requirement before temporary workspace cleanup. The private ledger and checkpoint transport are separate from public source code.
