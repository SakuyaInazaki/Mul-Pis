# Reusable private workflow requests

Code publication and paid workflow activation are separate. Ordinary commits to `improve/workflow-learning-reliability` run offline CI and cannot start the private campaign. A request uses `run-requests/workflow-learning-reliability`, with the stable commit message `Run confidential workflow`. Its commit SHA is the request ID; the message never needs a new marker in source.

Before creating a request, wait for a successful **Offline workflow regression** run on the current feature-branch tip. The control branch can first be created at that tip; its creation does not have the request message, so the private job is skipped. `node scripts/prepare-private-run-request.ts --source <full-feature-tip-SHA> [--previous-control <full-control-tip-SHA>]` prints a local descriptor only. It does not create or push a commit, verify remote CI, use a credential or start a paid run.

The request commit uses the descriptor's source tree and first parent. If the control branch already has a different tip, the second parent is that prior control tip. The resulting commit must fast-forward the control branch and have no tree changes relative to its first parent. The private workflow and host recheck the owner, repository, request ref, first attempt, exact message, source-branch tip and tree, successful offline CI, and authenticated cumulative carry before a provider call. Only an explicitly submitted request starts the job; `workflow_dispatch` remains an alternative where available. The workflow retains its existing read-only permissions, encrypted input and ciphertext-only output.

Track the request by its commit SHA and GitHub Actions run ID. A completed run writes an encrypted continuation and status artifact; the next request verifies that carry and any unresolved external operations before continuing. The request mechanism is reusable, but execution recovery still requires authenticated effect evidence. Zero-activity pass-through requires exact prior bundle preservation. Later runs carry host-generated task, operation, and live tool-grant receipts alongside per-request response/accounting observations. An append-only reviewed-effect chain binds each admitted nonzero predecessor to its authenticated carry and quarantine decision. Missing or unresolved external effects still block fresh execution; an unknown fee estimate alone is recorded rather than treated as a stop. An incomplete research goal is never called successful or silently replayed.

An ordinary M07 reviewer-ready verdict is followed by mechanical output validation and separate controller review. A recoverable file/schema failure is returned to the live builder for repair; if final controller review still rejects every candidate, that goal remains partial and a linked fresh goal may use the rejection and failed files as untrusted development evidence under the same constraints and success checks. The prior selected source remains selected until a new candidate passes the original checks and review. Historical uncertain charges and operations remain in the encrypted carry and quarantine chain.
