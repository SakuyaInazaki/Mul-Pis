# RSI 与 SoL-Pi：相对于既定科研执行流程的外部启发

> 状态：资料整理与比较研究，不是架构决定  
> 初次调研：2026-09-19；依据工作流逐文件深读修订：2026-09-20（Asia/Shanghai）

## 1. 比较前提

本项目的研究基础是 `workflow/v1.0`。它已经是一套面向泛科研的执行层设计，并明确说明不是从 RSI 论文移植，也不是需要“迁移为泛科研”的竞赛旧版。其已定内容包括 M01—M09 的按需协作、四类质询与评价语义、M04 统一处理纠错与状态更新，以及 C/K/E/J/Q/D/X 图式认识管理；原 v1 的网页版 AI 加用户人工转交链已在本轮由用户对齐为主 Agent 自动编排，见 [`workflow-foundation.md`](workflow-foundation.md) 的“当前对齐”。方向层、RSI 关系、具体存储、合入程序和自治程度仍属后议。

因此，本报告只回答两个问题：RSI 和 SoL-Pi 的研究结果与既定流程有哪些呼应；它们还提出了哪些尚待本项目自行验证的问题。它们都不能覆盖工作流原文，也不能仅凭这些外部材料就决定修改已定交互链或选定技术架构；材料仍可作为后议参考。工作流本身的逐文件解释见 [`workflow-foundation.md`](workflow-foundation.md)。

论文把科学 RSI 概括为强 L2、早期 L3（Fig. 9，p. 36），这是综述性定位，不是本项目应达到 L3 的要求。论文也说明端到端 L5 证据主要来自有界原型和新兴产业实践（p. 35）。据此只能确认“自治范围”和“改进是否有效”必须分别论证；本轮不决定自治上限、接受权或发布权。

## 4. SoL-Pi：方法事实、结果边界与可比较之处

### 4.1 官方系统实际做了什么

SoL-Pi 面向 coding-agent harness 效率，在 535 个可执行搜索环境中开发机制：495 个来自 GitHub issue—PR 对，40 个使用可执行 verifier。外层从 152 个提议方向展开，最后组合 4 个机制：Action Fusion、Online Context Compact、ObservationPack 和 Evidence-Preserving Reducer（论文 pp. 2—5；项目页 Method/Discoveries）。

候选线经过 trajectory rollout、map-reduce 分析、提议、实现、独立复核和开发集验证。实验前固定能力下限、允许容差和效率指标；候选需先满足能力下限，再改善至少一个效率指标。候选冻结后才进入 EdgeBench held-out，held-out 结果不回灌搜索，失败即拒绝（论文 p. 3、Fig. 2；项目页 Method）。这项纪律与工作流已有的候选判据、冻结待审版本、独立复核和事实/决定分离可以相互参照，但 SoL-Pi 没有验证工作流的 C/K/E/J/Q/D/X 语义或科研判断。

固定仓库快照将 SoL-Pi 定义为 Pi 的 standalone extension，不修改或 vendoring Pi；[README](https://github.com/NVlabs/SoL-Pi/blob/bd005888b9b8a3fcdb511feb91fc27d3dfa8f2b1/README.md)与[安装说明](https://github.com/NVlabs/SoL-Pi/blob/bd005888b9b8a3fcdb511feb91fc27d3dfa8f2b1/agents-install.md)写明测试目标为 Pi `0.85.1`。[配置说明](https://github.com/NVlabs/SoL-Pi/blob/bd005888b9b8a3fcdb511feb91fc27d3dfa8f2b1/docs/configuration.md)显示四个机制默认关闭、需显式启用。这些是 SoL-Pi 自身的封装事实，不等于本项目已经选择 extension 架构。

### 4.2 结果必须保留的代价与范围

| 结果 | 可以说 | 不能说 |
|---|---|---|
| EdgeBench：GPT-5.6 Sol 的 SoL-Pi Efficiency 保留 Pi 平均得分的 93.7%，令牌少 49.0%；Opus 5 则保留 94.3%，令牌少 44.7%；两者成本均约低三分之一 | 在所测两个后端和该任务集上形成质量—成本折中；Table 1/2 的总体 EdgeBench 结果未统一注明推理档位，Fig. 7 的 GPT-5.6 Sol 合并机制分析另标为 `xhigh` | “能力无损”或对泛科研同样有效 |
| Terminal-Bench 4：SoL-Pi 15/63，Pi 与 Codex 各 18/63；总成本 $211.12、$286.45、$272.35 | 成本降低同时伴随解题数下降 | 只凭成本宣称完整系统更优 |
| “recursive efficient improvement” | 作者提出效率可能降低下一轮搜索成本的愿景 | 已证明递归复利；论文明确说尚未证明（p. 12） |

论文还报告：机制由单一 LLM 的轨迹训练，在另一后端触发更少；完整 auto-research loop 计算昂贵；证据仍是初步的（p. 12）。项目页保留了人类提供先验、筛选探索方向、理解幸存机制和重构代码的角色。因而它给出的强证据是“有可执行 verifier 的 coding-agent 效率优化”，不是“泛科研工作流有效”。

### 4.3 与既定流程可比较、但不能替代的内容

- SoL-Pi 的候选隔离、开发/held-out 分离、冻结标准和保留失败证据，可用于检查未来工作流评测是否泄漏；它们不改变 M04 已定的采用、限定、暂停、撤回与未决处理。
- coding verifier 只覆盖软件行为。科研主张还需按既定流程保存来源、条件、论证、反例、领域检查和当前可用性。
- “约 94% 能力”不是本项目的可接受容差。来源忠实、统计有效、数据完整、隐私、安全和可复现性是否允许退化，仍待具体任务与用户决定。
- token、成本和时间属于工作流表现证据，不能代替科研结果证据。当前工作流已经区分执行事实、论证和采用决定，这可为以后讨论改进证据提供基础；如何表达工作流改进证据尚未决定，不能直接认定已有双账设计，也不应在后议完成前另造平行账本。
- SoL-Pi 没有为 M03 的承载方式提供证据。原 v1 的网页版 AI 加用户人工转交链已由用户在本轮对齐为主 Agent 自动编排；该变更来自用户决定，不来自 SoL-Pi。后续承载方式的比较仍应作为明确议题另行决定。

## 5. 自我改进仍是后议

外部材料支持把下列问题留给后续决策，而不支持本轮预选答案：

1. 系统只观察和提出候选，还是还能隔离实现、运行评测、建议采用或自行发布？
2. 哪些研究任务构成开发集和 held-out，怎样防止候选或评价器接触保留集？
3. 哪些科研保护项要求零退化，哪些可接受有统计依据的容差？
4. 谁能修改接受标准，谁能处理采用、停用、撤回和发布？
5. 工作流改动证据怎样引用科研执行事实，同时不冒充科学结论证据？

“候选隔离评测后由人批准”可以在下一阶段作为一个比较选项，但不是用户已经接受的默认路线。自动回滚也不能直接套用：工作流已明确，历史回放或完整更新失败不得取消已知停用与权限限制；任何实现都要先满足这一语义。

## 6. 对下一阶段的有限输入

RSI 提供描述自治和持久改进的外部坐标，SoL-Pi 提供 coding-agent 场景中候选筛选与 held-out 纪律的实例。二者共同提醒要区分：过程变快、harness 能力变化、科研结论成立、规则获得采用授权。这些区分在 `workflow/v1.0` 中已有更具体的对象和状态表达，后续讨论应从原工作流出发核对承载能力，而不是反向用论文术语改写它。

当前工作止于资料整理、关系澄清和证据边界。未选择 Pi 承载结构、知识存储、事务方案、自治级别、接受规则或发布机制，也不在本轮实现任何一项。

## 7. 未验证项

- `workflow/v1.0` 尚未在代表性的非数学建模科研任务上完成实际 A/B；它已被设计为泛科研，不等于效果已验证。
- SoL-Pi 项目页和论文属于同一研究团队，不是独立重复。
- RSI 与 SoL-Pi 都是近期 v1 预印本，后续版本可能修订结论或数字。
- SoL-Pi 固定 SHA 已核验，但未来版本行为不能从该快照推出。
- 本项目尚未确定任务分布、held-out 构造、保护项、容差、评测独立性和自治权限，因此不具备声称“自我演进方案已定”的条件。
