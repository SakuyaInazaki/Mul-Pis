# Project Working Rules

## Scope

- This repository is a documentation and research baseline for a general scientific workflow carried by the Pi agent harness.
- Do not claim that a runtime research engine or self-improving research system exists unless executable evidence is added and verified.
- The current research-execution layer uses `workflow/v1.0/` as its original baseline. Current stage alignment is recorded in the “当前对齐” section of `docs/research/workflow-foundation.md`; RSI and workflow self-improvement are later topics, not current execution-layer rules.

## Workflow ownership

- `workflow/v1.0/` is the user's own workflow and the direct foundation for continued research and evolution.
- Changes to the workflow must follow the user's current request and preserve relevant history, but the directory is not an immutable imported artifact.
- Put research mappings and implementation guidance under `docs/` when they are supporting material rather than workflow content.
- Do not introduce file-hash manifests or hash-verification workflows unless the user explicitly requests them.
- Publish original logs, task records, and supplied attachments only within the user's explicit release scope. Keep account authentication material out of publication, and do not imply rights to third-party material beyond the user's supplied scope.

## Third-party and local-only material

- `third_party/` contains local upstream checkouts. Do not modify their source from this repository task.
- Follow a checkout's own `AGENTS.md` for any separately authorized work inside it.
- Keep `third_party/` out of public release artifacts. Do not track active `resources/` or `.agent/private/` trees directly; when the user explicitly authorizes original evidence and attachments, use a reviewed archive that preserves source bytes and excludes authentication material.
- Record third-party URLs, licenses, versions, and full Git commit hashes in `docs/provenance.md`.

## Change records

- Record every project change batch, including documentation, configuration, migration, and deletion, in `.agent/notes/`.
- Review and redact project change notes before publication. They may be committed with the corresponding change after omitting machine-specific absolute paths, credentials, raw chat transcripts, private identity data, and test-specific material. Keep original sensitive versions under `.agent/private/` locally.
- Before destructive operations, record the exact target, why removal is necessary, and whether it is recoverable. Prefer archiving when practical.

## Collaboration

- For work on this Codex repository, the main agent owns requirement clarification, implementation-design judgment, orchestration, and acceptance. This does not move the workflow's substantive M04 scientific judgment away from the research session and model to be chosen later.
- Prefer delegating bounded implementation, large code reads, bulk changes, and tests to execution subagents when the environment supports them.
- The model requested for execution in the current Codex project session is `gpt-6-sol`.
- These collaboration rules do not assert that Pi already provides the same subagent behavior and do not select a future Pi model-routing design.

## Current implementation boundary

- On 2026-09-20 the user authorised implementation of the research harness after the alignment pass. The implementation lives in `src/` (TypeScript on the local Pi 0.85.1 SDK), with tests in `test/` and the design record in `docs/implementation/design.md`.
- Scope of the current implementation: workspace init, M01–M06 session orchestration with real input isolation, M07 persisted goals and bounded task delegation/review, M08 fixed-version self-check and external review batches, M09 paired M08/M04 explanation and delivery verification, the C/K/E/J/Q/D/X knowledge store with a single serial merge entry, a CLI, and an explicit Pi extension loaded with `pi -e ./extensions/research.ts`. M05 uses browser-use (user-recommended) and Crawl4AI plus public HTTP search endpoints (OpenAlex, arXiv, Crossref, Hacker News, Stack Exchange, Reddit, GitHub repositories and issues, DuckDuckGo HTML, optional Brave API key), behind the replaceable `AcquisitionBackend` interface; it supports scoped continuation and preserves browser page/text/screenshot/download artifacts for M06 with per-file provenance, without claiming exhaustive coverage. PDFs are handled with poppler only (text layer plus on-demand page images for multimodal models). The user does not want local ML models or Docker: do not add Docling, OCR models, SearXNG containers or similar local services. The Python stack lives in `.venv/` (ignored) and is installed by `scripts/setup-tools.sh`. M07–M09 run synchronously in the invoking Pi tool call and do not implement detached jobs or process-restart replay. A separately invoked first improvement loop may propose only the fixed budget/evidence-handoff policy schema, screen it with the controller-owned offline evaluator, require controller-executed paired local-mechanism admission using caller-supplied cases before any automatic promotion, serialize mutations with a workspace lock, and compare the active pointer with the frozen baseline before atomically promoting an admitted candidate, and roll back the active pointer. New M07 goals freeze the current policy; promotion or rollback affects only later goals. Legacy goals without a snapshot remain viewable and may be interrupt-archived with control-facts-only feedback, but cannot continue normal delegation or completion. Residual locks require owner and transaction checks; only a verified dead owner under the new same-host recovery protocol may be taken over automatically. Legacy or unknown owners remain fail closed for exact manual review. The loop must not modify workflow source, evaluator policy, or knowledge limits. Historical runs are development replay rather than a blind held-out set; general research benefit, source self-modification and multi-generation RSI remain unverified.
- The first improvement loop now requires an explicit bounded campaign plan. It samples actual M07 task-message and feedback projection events with separate UTF-8 bytes and UTF-16 units; missing or over-budget controller snapshots are unreplayable, and provider tokens remain separate. The deterministic projection replay is a screen, not admission. Automatic promotion also requires caller-supplied admission cases with repeated fresh baseline/candidate sessions, fixed hard checks, complete visible usage and a strict estimated-cost improvement. This is a local mechanism experiment, not proof of end-to-end scientific benefit. Method export carries policy and limited metadata; binding into another workspace is an explicit external import marked unverified. Pi orchestration usage is separately observable and cannot automatically be attributed to one campaign; hidden retries, external resources, actual provider invoices, and human work are not covered by the campaign ledger.
- A separate bounded research-method slice versions an executor strategy (H) and an improver strategy (I) as data-only methods actually loaded into their sessions. The currently implemented environment is a fixed-unit CPU response-identification task with a finite hypothesis set, controller-owned probes, separated development feedback and protected checks, fresh paired arms, and explicit root/child budgets. Those budgets cover calls started by this research campaign, not the extension's separately observed Pi main-session orchestration or all project/model costs. Controlled I/H child sessions have no general tools and do not receive protected G results; this is context isolation, not OS isolation of private cases from a main Pi session with ordinary file or bash access. An evidence-based justified unknown is partial quality, not a solved case or a wrong guess. This is not a general numerical research environment, asynchronous job system, source-code candidate execution system, or OS code sandbox. Existing C/K/E/J/Q/D/X records remain the only knowledge store: M04 remains the adoption path; explicit pinned `{storeId, recordId, version}` experience refs are checked for applicability, required dependencies and live limits before a bounded pack enters the I decision context or an explicitly requested M07 task. Versioned H/I methods retain loaded source refs and inherited required refs; omission from a later plan cannot clear the latter, and new calls, activation, rollback and V2 import recheck them. Selection or loading is not faithful use, scientific verification, or causal benefit. Withdrawal blocks old versions and necessary dependent use; historical records remain readable. Development feedback and model hypotheses must never be written as verified/adopted facts without the existing M04 decision path. Engineering tests and small real-model H and I development action chains show the environment is wired, but I selected no successor and no complete real-model paired H/I admission or independent executor/meta gain has been established; structural L5, L3/L4 recursion, and general scientific benefit remain unverified.
- The next bounded method increment adds explicit between-campaign `advance-knowledge` after a completed M04 merge, with a new snapshot, no running campaign, active-pointer compare-and-swap, and inherited live-reference checks; old runs and H/I bodies remain intact. Method records distinguish consulted `sourceExperienceRefs`, legacy conservative `requiredExperienceRefs`, and structured necessary scientific `requiredKnowledgeRefs`. An exact M04 adopted D decision plus registered evidence and revalidation can create a new method version changing only the latter; this does not revoke store limits or prove scientific correctness. Meta searches may use one frozen bounded nonempty experience selection for both fresh arms; development-only MetaEpisodes precede protected checks. Explicit M07 `m07-workflow-prompt` H slots enter the real task prompt and evidence handoff without overriding goals, mandatory checks or tool authority; CPU H cannot fill those slots. Loaded, faithfully used, and beneficial remain separate claims. The 24-item review catalog is not a passed test suite: engineering regressions cover selected controls, further real-model comparisons are pending, and replay/async platform ambitions remain outside this batch.
- Explicit noninteractive Pi continuation applies only to a configured workspace and bound M07 goal in one live session. A normal model turn end can queue another turn while that goal remains active; only persisted controller evidence permits `fulfilled`, while aborts, errors and repeated no-progress turns stop with an incomplete reason. This does not resume a crashed process or replay a running child task. M07 feedback under the frozen policy reports `complete`, bounded `indexed`, interrupt `control-facts-only`, or repair-needed `failed`: a long full package may become an index to retained `goal.json` and frozen evidence without changing the goal's success checks or its budget. M04 must actually read indexed material in ranges; a saved path or fulfilled controller state is not proof of full reading or scientific validation.
- Runtime recovery is now a separate, explicit fresh-attempt path for newly versioned M07 goals; it never replays an execution session or silently changes a historical `finished/blocked` goal. The host records a small control checkpoint while keeping a suspended goal active, then verifies the old attempt, frozen policy/H/K, and the new Pi process identity before binding a successor attempt. Unknown external operations block renewed execution until independently reconciled. Legacy goals keep their earlier interrupt semantics and may require an explicit linked successor. This mechanism has offline engineering tests but no real restarted research goal acceptance yet.
- A shared run descriptor pairs PID with host, boot and precise process birth identity. `workflow:control` reports stored and observed state separately and signals only a verified independent process group; an old PID file alone is not authority. Only a trusted pause record offsets watchdog time. The private launcher rotates retained main-log segments with an independent disk free floor and offers bounded fixed-file observation; observer failure must not change the research goal. These are control-layer guarantees, not proof of scientific progress.
- Knowledge merge uses a frozen prepared/committed intent and a recovery gate. A verified dead owner on the same host and boot can be taken over with the old lock retained for audit; live, reused PID, unknown or legacy PID-only owners remain fail closed. CURRENT publication and result recovery are reconciled before another merge, preserving negative limits. This does not provide distributed multi-host transactions.
- M08 reviewers are an explicit caller-provided list; the harness never chooses their count or treats agreement as proof. M09 may deliver only paths allowed by the named M04 run's validated M08 disposition and never publishes, submits, sends, starts another goal, or starts RSI. Requesting full recomputation records the requested and actually executed scope; it does not certify full reproduction.
- The harness never chooses a model: every role's model comes from the workspace `research.config.json`.
- Tests must not call real models or the network. Dependencies resolve through `node_modules/` symlinks into `third_party/pi` (ignored by Git); do not run `npm install` against the network without the user's request.

- For the current preparation pass, initialize a repository, create a remote, commit, and push only after the user accepts the organized result. In later work, follow the authorization scope of the active request.
- Do not choose a project license on the user's behalf.
- Before release, simulate the public file list and confirm local-only material and nested `.git` directories are excluded.

- Follow `docs/github-push-policy.md` before every commit and push.

For this release, the user also authorized original logs, run records, test-task material, platform details, and supplied attachments, including their internal paths and identifiers. Publish them only in the reviewed byte-preserving evidence archives; exclude account authentication files and actual account API keys. Do not track active `.agent/private/`, `.agent/telemetry/`, `workspaces/`, or `resources/` trees directly.

- Run typecheck and tests before push. History rewrite and force push require explicit user authorization and an external bundle backup.
